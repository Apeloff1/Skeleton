# Docker local-AI — two independent signatures over offline file custody

**Review-only independent provenance. Not a release, not a valid database
recovery and not a protected Jeeves chat authorization.**

## Purpose

The v2 read-only offline recovery ledger binds independent MongoDB
WiredTiger static file inventory, SQLite page/foreign-key integrity and
Chroma historical HNSW byte custody. Those checks produce useful evidence
that bytes survived an offline archive. They do not establish actual
mongod journal replay or cross-store transaction consistency.

This source adds a separate verification layer: two independent external
Ed25519 authorities must have signed the *exact same strictly canonical
file-custody claim*, and the verifier must recompute the whole v2 evidence
against the private source archive before and after checking signatures.

## Operator action

```sh
python scripts/local_ai_docker.py --mode cpu verify-signed-offline-custody \
  --claims-directory /private/existing-signed-custody-bundle \
  --operator-public-key /independent/operator.pub.pem \
  --auditor-public-key /independent/auditor.pub.pem \
  --source /private/existing-cold-archive \
  --destination /private/existing-rehydrated-copy \
  --expected-source-head-sha EXPECTED_EXACT_GITHUB_COMMIT_SHA40 \
  --expected-receipt-sha256 ORIGINAL_INDEPENDENT_ARCHIVE_RECEIPT_SHA256
```

The bundle must be an already-existing, owned, private directory
containing **exactly three** files:

- `offline-three-store-claims.json`
- `operator.ed25519.sig` (raw detached Ed25519 signature, exactly 64 bytes)
- `auditor.ed25519.sig` (another independently generated 64-byte signature)

The *public* keys must be supplied independently from outside the signed
bundle. Two paths containing identical key material are rejected.
Private keys are NEVER loaded or generated by the verifier. Do not
put a private key in the application or the evidence directory.

## Exact signed manifest contract

The manifest is a single canonical ASCII JSON object with sorted keys,
compact separators, a final newline, no extra fields, no duplicate
keys and no nonfinite values. Its required members are:

- `schema`: `skeleton.local-ai.docker.double-signed-offline-custody.v1`
- `status`: `signed_file_custody_not_database_recovery`
- `source_head_sha`: exact 40-character lower-case GitHub commit SHA
- `cold_source_receipt_sha256`: exact independently communicated
  original cold-archive receipt digest
- `aggregate_evidence_sha256`: digest from a fresh v2 three-store
  physical file-custody ledger
- `signer_domains`: exactly `["operator","auditor"]`
- All recovery and authority claims strictly FALSE:
  `mongo_logical_recovery_qualified`,
  `sqlite_semantic_recovery_qualified`,
  `native_chroma_graph_qualified`,
  `source_writer_quiescence_verified`,
  `cross_store_transaction_coherence_qualified`,
  `application_restore_qualified` and `release_authorized`.

Keys inside the evidence bundle are never trusted, even if signatures
mathematically verify. The two out-of-band PEM public keys must be
distinct, owner-controlled and declared explicitly to the operator.

The source intentionally does **not** provide a signing command or
write private keys. Signing is done separately by the operator and an
independent auditor outside the protected application environment.

## Admission and remaining holds

The verification steps are ordered:

1. Inspect the owned private bundle; deny unexpected members.
2. Independently read and validate two outside Ed25519 PEM public keys.
3. Read the exact canonical manifest, deny authority escalation, and
   validate the exact repository head and original cold receipt hash.
4. Demand the two fixed-length detached signatures.
5. Independently re-execute the v2 Mongo/SQLite/Chroma byte-custody
   ledger and compare its real observation digest with the manifest.
6. Verify both Ed25519 signatures using bounded OpenSSL commands
   without a shell and without emitting OpenSSL diagnostics.
7. Re-read manifest, signatures and public keys to reject observable
   post-validation mutation.
8. Re-execute the full source-byte and three-store evidence ledger again.
   Both physical observations must be exactly identical.

The final receipt is **still only file custody**. It never claims
physical Mongo log replay, independent source-writer quiescence,
native vector query, cross-store atomic consistency, protected
Jeeves inference, device qualification, merge or release authority.

Even valid cryptographic signatures are not evidence that an
application-level backup was atomic or that its original signers were
authorized to approve production recovery. This module does not assign
those privileges.

## Focused exact-head source qualification

```sh
python -m compileall -q \
  scripts/local_ai_signed_custody.py \
  skeleton/testing/test_local_ai_signed_custody.py \
  scripts/local_ai_docker.py

PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q --noconftest \
  skeleton/testing/test_local_ai_signed_custody.py \
  skeleton/testing/test_local_ai_offline_three_store.py \
  skeleton/testing/test_local_ai_restored_mongo.py
```

The source suite generates temporary Ed25519 keys **only within the
temporary test fixture**, exercises real OpenSSL Ed25519 signing and
verification, then destroys the fixture with the test runner. It tests
independent keys, wrong signatures, malformed or duplicate JSON, exact
manifest custody, forged recovery flags, false physical receipts,
post-signature source drift, raw-error redaction and no Docker access.

The test fixture's keys and signatures are not production evidence and
must not be re-used for deployment or distributed to users.
