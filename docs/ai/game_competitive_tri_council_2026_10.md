# Competitive Tri-Council - 102-facet scrutiny, user critique, Dragon research and multipart PDFs

Status: implemented control plane on PR #3644, stacked on PR #3643 and #3642. No actual competitor game has been legally crawled, measured or outperformed by virtue of this code alone. Original game quality is NEVER inferred from file counts or synthetic tests.

## 1. Doubling real adversarial scrutiny

102 individually testable, full-coverage probes: Gameplay 28, Graphics 24, Sound 22, Storyline 28. The new 51 probes are independent controlled experiments, not repeated synonyms. Every probe defines a question, controlled situation, measurable outcome, negative stress condition, exact protocol/scenario digest, platform, approved knowledge source and originality review.

Gameplay additions include safe save recovery, exploits and economic fairness, adversarial AI counterplay, network jitter, stable physics, procedural solvability and intentional nonwinning worlds, haptics and offline resilience. Graphics additions include real frame-time tails, upscaling, shader variants, LOD, motion comfort, rendering truthfulness and GPU memory. Sound additions include occlusion, caption synchronization, streamed banks, accessible mono fallback, original score identity and musical narrative state. Storyline additions include quest deadlock, rumor epistemics, nonlinear chronology, NPC relationships, long-horizon memory, time paradox, ethical choice and causal emergent-world history.

Never truncate the evaluation to first 51. Both the competitor and its strongest verified historical ancestors must remain in the evaluated cohort.

## 2. Constructive criticism of the CURRENT USER PROJECT

The user project is bound to its current instrumented build digest, source tree, frozen original design, target platform and captured timestamp. Every one of 102 facets receives a criticism object: observed state, what is unknown, what may be improved, how to implement something original, exact replay protocol, required evidence, severity and identity pillars to preserve.

A separate signer binds every submitted current-game measurement digest to the build identity. No live game study means all such facets remain UNMEASURED. A code repository or AI-generated report cannot claim gameplay has been independently evaluated. No third-party asset, code, soundtrack, story, image or video is copied to the proposed original project.

## 3. Exactly three rounds, all three model roles

Round 1: Focused research and first constructive project diagnosis; at least 2 independent reviewed source identities in 2 groups. Round 2: fresh contradictory and broader research; at least 4 sources in 3 groups, including all earlier source identities. Round 3: wider genre/platform/era research; at least 6 sources in 4 groups and a strictly newer reviewed Wiki source root.

Every round must be current in the existing ReviewedKnowledgeStore AND RightsLedger. Evidence must be legally cleared and source dependence must be real, never inferred from re-posted peer articles. After user rejection the next epoch doubles source requirements at epoch 1 and requires more independent publisher groups, with increased native Dragon discovery budget (bounded to protect consumer-grade hosts).

Three separately signed role outputs per round:
- Dragon: source independence, lawful acquisition, peer/video/blog provenance, rights and game almanac training permissions.
- Jeeves: conditional causal reasoning, game-engine dependencies, user experience, new original mechanics, implementation feasibility and performance budgets.
- Adversarial Mirror: falsification, counterfactual game cases, objective benchmarks, originality/safety vetoes, potential regressions and proof standards.

Every role's review must explicitly enumerate all 102 facets, cite actual reviewed source hashes, propose multiple falsifiable improvements, challenge another role, answer counterarguments, satisfy a predeclared quality bar and use a distinct operator-configured credential. One low score or critical veto blocks advancement. Signer names alone cannot establish real LLM inference or independently verified human identity; actual authenticated actor runtimes must supply each review.

The user may request rework during any round; previous partial authority is invalidated and new source evidence is required. Only successful three-round packages can enter the end-user approval phase.

## 4. Existing Dragon crawler used, not forked

The new competitive research mission adapter reuses the native Dragon research planner in skeleton/ai/webcrawler/dragon_research_missions.py. It preserves separate source acquisition policies and returns future work, not fake completed fetches. Research topics begin at 6 (24 discovery query intents), expand to 12 (48) and then to 20 (80). Four research domains are reserved before global importance selection. A rejected plan escalates the budget within a 20-topic ceiling.

Discovery backends already include Wikipedia, Crossref, OpenAlex and Europe PMC. Third-party APIs, metadata and URL results remain untrusted until a rights reviewed Wiki claim is independently verified. Host execution must enforce access terms, robots policy, rate/thermal limits, safe DNS, redirects and privacy. RFC 9309 is a crawler protocol, not model-training copyright permission.

## 5. Strict 3 x 3 PDF production

The repo's deterministic competitive_pdf_pack.py produces three separate PDFs (Dragon, Jeeves and Adversarial), with exactly three A4 pages EACH. Every document has Parts I / II / III:
I. source-backed current user project criticism;
II. three distinct research passes, new evidence and peer cross-examination;
III. original-game implementation demands, measurable acceptance and explicit user decision.

It enforces a page-line budget, fails on overflow rather than silently truncating, and does not execute PDF embedded scripts. The three files, a canonical JSON manifest with their cryptographic digests, and a ZIP form one immutable multipart review packet. The manifest binds original-game snapshot, the 3 actual crawler research digests, all model role reports and user approval state.

Separate architecture-informed draft PDFs were also produced for review in the current chat; they do not falsely claim execution by native models or the user's approval. Production packets require authenticated model-service submissions.

## 6. User approval: all or nothing

A native packet inspector checks exact SHA-256 manifest identity, exactly three PDF files, exactly 3 pages per role, exact ZIP parity, file digests, source roots and explicit pending approval status. An operator must separately acknowledge all three documents.

The local manual CLI in competitive_battle_review_cli.py has inspect, approve, revise and defer commands. Approved/rejected decisions need an authenticated host-provided 256-bit session signing secret, user session context digest, timestamp and entire reviewed packet SHA. The key is provided by the host environment, never stored in PDFs or passed as CLI text. Decisions are immutable, cannot be silently overwritten, and never directly deploy game code or neural weights.

If the user rejects, feedback must be substantive and a higher-effort, wider source-acquisition epoch begins. If a plan fails at any earlier stage, the operator can request full strategic restructuring without first pretending the three role reviews succeeded.
