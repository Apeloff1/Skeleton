# Jeeves: private selected-source capsule (cold local-first delivery)

## Capability

The original locally installed GGUF and SQLite-authorized source-generation
sequence ends with an owner-private `*.source.json` file, generated by a real
operator-approved native model request. The existing cold source delivery
workbench can export a reviewable Git patch or stage changed files. A changed
file overlay alone does not contain unmodified modules required for human
inspection or controlled downstream testing.

This extension builds a **new private selected-source capsule**. It includes
both the exact model-proposed new and edited files and up to 48 explicitly
selected, independently read original dependency files. The resulting
directory is not a Git checkout, complete project, execution sandbox, model
authorization or release artifact. Any unselected import or resource remains
unverified.

The capsule is source-only. The product does not execute Python, Git, shell,
models, tests, compiler output, user-provided build scripts or plugins. A
human must separately inspect the resulting source and decide how to test or
apply it.

## Cold inspect, approve and verify

Run all commands from the repository root on a supported trusted POSIX/WSL2
environment. The project must be owner-controlled, and the private destination
parent must be a pre-existing owner-private directory. The destination
directory itself must **not** exist.

1. Keep the **original** exact job SHA, private proposal file SHA and byte count
   from the successful GGUF source-generation receipt. Do not invent or
   truncate these hashes. Ensure the proposal is the exact cold, private file
   created by the native escrow command.
2. Human-select 1–48 extra existing source files that are not being edited in
   the patch. Provide exact repo-relative paths in a newline-delimited string,
   not glob patterns. Each source must be UTF-8, regular, under 64 KiB, safe
   under the existing source blocklist, and non-symlinked. The selected
   originals are separately read from the real checkout.
3. Run **inspect** first. Feed a single JSON object through stdin to
   `python scripts/jeeves_native_capsule.py`. The response contains the
   resulting full `capsule_sha256`, original `source_manifest_sha256` and
   `patch_sha256`, along with every selected original and proposed
   replacement path and exact digest.
4. Inspect the model source and full Git patch separately using the existing
   secure private workbench. Review the selected original files and intended
   changed sources. Only then run **publish** with all three original full
   digests and `--approve-private-capsule`.
5. Publish writes a **new** 0700 owner-private directory; files are 0600. For
   each file, a pinned no-follow descriptor writes and rereads the exact bytes,
   then fsyncs the private file and directory. All original sources are
   revalidated before and after publication. The canonical JSON completion
   seal `.jeeves-source-capsule-seal.json` is written **last**.
6. Independently run
   `python scripts/jeeves_verify_private_capsule.py` with an explicit full
   capsule SHA and the **seal SHA** from the publish receipt. This cold
   verifier checks all sealed source bytes, owner/mode/inode, no unexpected
   files/dirs/symlinks, exact paths and final digest; it does not need to
   open the original GGUF model, SQLite database or project files.

### Inspect request

Put this JSON in an owner-private input file or pipe it directly. All values
with `<...` must be replaced with actual original data; the example is not
a runnable authorization.

```json
{
  "schema": "jeeves.workspace.native-private-source-capsule-cli.v1",
  "action": "inspect",
  "project_root": "/absolute/operator/project",
  "saved_proposal_file": "/absolute/private/model.source.json",
  "expected_saved_file_sha256": "<64-lowercase-hex-of-private-escrow-file>",
  "expected_saved_file_bytes": 1234,
  "expected_job_sha256": "<64-lowercase-hex-of-reviewed-native-job>",
  "selected_sources": "src/dependency.py\nsrc/constants.py",
  "target": null,
  "source_manifest_sha256": null,
  "source_patch_sha256": null,
  "capsule_sha256": null
}
```

### Publish request

```json
{
  "schema": "jeeves.workspace.native-private-source-capsule-cli.v1",
  "action": "publish",
  "project_root": "/absolute/operator/project",
  "saved_proposal_file": "/absolute/private/model.source.json",
  "expected_saved_file_sha256": "<64-lowercase-hex-of-private-escrow-file>",
  "expected_saved_file_bytes": 1234,
  "expected_job_sha256": "<64-lowercase-hex-of-reviewed-native-job>",
  "selected_sources": "src/dependency.py\nsrc/constants.py",
  "target": "/absolute/private/new-source-capsule-001",
  "source_manifest_sha256": "<64-lowercase-hex-from-inspect>",
  "source_patch_sha256": "<64-lowercase-hex-from-inspect>",
  "capsule_sha256": "<64-lowercase-hex-from-inspect>"
}
```

Invoke with `python scripts/jeeves_native_capsule.py
--approve-private-capsule` (flag on the command, JSON via stdin).
Without the flag, all publish requests hold; inspect requests reject the
flag. All unknown JSON fields, duplicate keys, nonfinite values, partial
hashes, unapproved source destinations, unexpected files and stale original
sources hold fail closed. Passing the flag alone never authorizes mismatched
original hashes.

### Independent verification request

```json
{
  "schema": "jeeves.workspace.cold-capsule-verification-cli.v1",
  "capsule_directory": "/absolute/private/new-source-capsule-001",
  "original_project_root": "/absolute/operator/project",
  "expected_capsule_sha256": "<64-lowercase-hex-from-inspect>",
  "expected_seal_sha256": "<64-lowercase-hex-from-publish>"
}
```

Invoke with `python scripts/jeeves_verify_private_capsule.py`.
It is read-only, needs no approval flag, and cannot apply or execute files.

## Bounded assurance contract

- Original selected source: **1–48 files**, each at most 65,536 bytes, aggregate
  at most 1,048,576 bytes. The existing reviewed patch supports at most
  24 new and/or edited files.
- All capsule source (selected originals plus replacements): at most
  1,572,864 bytes across at most 72 source files. Relative path restrictions
  and credential/control file denylist are inherited from the existing
  workspace source reviewer. Path selection is explicit rather than globbed.
- Read-only inspection pins the original root and each original file's
  inode, device, mode, ctime, mtime and exact UTF-8 SHA. The same constraints
  must pass before and after capsule publication. Existing changes retain
  their independently verified original-source SHA and current source checks.
- New capsule name must be bounded ASCII; all owner-private destination
  parents must already exist outside the project tree. Publication uses
  `O_NOFOLLOW`, `O_EXCL`, 0700 private directories, 0600 private files,
  full readback and fsync. New directory creation cannot overwrite a
  previous directory.
- The cold verifier performs a no-follow tree walk, rejects undeclared
  files and symlink/alias/special inode replacements, rejects noncanonical
  JSON seals and reopens the same final seal after the tree audit.
- A power loss, source change or rejected write can leave an **unsealed
  incomplete private directory**. Such a directory is a HOLD, never a
  completed capsule. The program does not automatically delete private
  output, retry uncertain operations, or overwrite a pre-existing target.
- The model and generated code never receive local filesystem, shell,
  network, Git or authorization tooling. Public receipts contain paths and
  hashes, but **no source contents and no private absolute paths**.

## Qualification status and limits

Source-only Python unit fixtures exercise real mixed new/existing source
proposals, real original inode checks, capsule completion and independent
readback, exact consent, drift, symlink/extra file and crash-before-seal
refusals, and strict CLI parsing. They do not prove a real installed GGUF
execution on a Windows 11/WSL2 laptop, usable UI, packaged source imports,
that a runnable project is complete, that any generated code is safe to
execute, or that the repository is release ready.

The existing draft dependency chain, fail-closed security policy, physical
GGUF/license validation, and all final-head CI and release gates remain in
force. No mutation of original project files, Git index, Git branch or release
status happens in this capability.
