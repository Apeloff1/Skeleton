# Native architecture and response-only optimizer

The implementation uses a real CPU TinyTransformer already present in
Skeleton. It has learned token embeddings, positional information,
attention projections, normalization, feed-forward transforms and an
output projection. The model starts from seeded actual weights, not
a canned string responder or external API fallback.

A train-only vocabulary comes from 432 framed original prompt/answer
pairs. Native chat framing is generated by the same ChatTranscript
formatter used during serving. Every expected answer is separated from
the prompt before computing gradient targets.

The window builder generates one causal context and next-token target
per assistant answer token. The first context is exactly the framed
user request and assistant prefix. Later windows append already known
target tokens as teacher forcing. There are no prompt-token gradient
targets. Blank completions and oversized contexts are rejected.

All target windows are prepared before SGD begins. Their source IDs
are verified as exactly the 432 train IDs, never any validation,
holdout or challenge ID. The number of intended optimizer updates
must fit the declared policy across all epochs.

Real SGD uses the existing native _sgd operation on each response
window. It computes a bounded cosine learning rate with an explicit
positive floor, checks native step counters after batches and records
epoch identity, source-window SHA and elapsed time.

For independent validation, the model produces actual output logits.
Numerically stable log-sum-exp cross entropy measures answer-token
loss; nonfinite logits and nonfinite aggregate results fail closed.
Each epoch is evaluated against the same original validation windows.

The model candidate is selected only if its measured validation
loss beats the initial loss by the declared threshold, remains inside
the loss ceiling and round-trips to the same tokenizer/model digest.
The selected checkpoint is candidate-only even if its measurements
look favorable.

The reference CPU path is not optimized multi-GPU training, distributed
mixed precision, large-model throughput or hardware certification.
Those are separate capabilities requiring their own implementation
and actual performance qualification.
