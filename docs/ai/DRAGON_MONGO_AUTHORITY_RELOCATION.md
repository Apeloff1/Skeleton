# Dragon offline Mongo authority relocation

The crawler's two authoritative collections (`dragon_crawler_sessions` and `dragon_crawler_commands`) can be copied to an explicitly dedicated Mongo database, including historical records, tombstones, fences, references to external manifests and quota/command records. Other application collections and account/identity authority remain in CORE_DB. External SQLite/payload storage and derived-index custody must be handled separately. This does not replace or modify the existing terminal cold-primary payload relocation protocol.

## Operator procedure

1. Stop all backend instances, scheduled workers, old readers/writers capable of mutation and external maintenance. Take validated source Mongo and local-store backups. Use a new destination database with a distinct name. Restrict source credentials to read-only plus topology inspection where supported. Configure `MONGO_URL`, `DB_NAME`, `SKL_DRAGON_TARGET_MONGO_URL`, and `SKL_DRAGON_TARGET_MONGO_DB` in the operator environment. Never place credentials in arguments, reports or repository files.
2. From backend: `python -m core.dragon_mongo_relocation prepare --offline-writers-stopped`.
3. Repeat `python -m core.dragon_mongo_relocation copy --batches 8 --offline-writers-stopped` until ready_for_verify. Batches contain at most 128 documents; at most 64 batches per call. Raw BSON bytes and ordered string identity are preserved, duplicate insertion is accepted only if the destination bytes match, and a majority-acknowledged target journal checkpoints each completed batch. Interrupted copy resumes. The tool does not support concurrent operators.
4. `python -m core.dragon_mongo_relocation verify --offline-writers-stopped --receipt /private/path/dragon-relocation.json`. Verification recreates supported indexes, checks both collection UUIDs, exact source and target ordered raw-BSON fingerprints, counts and bytes, and rechecks the source after target verification. Any drift or unsupported schema holds. No source deletion or automatic rollback.
5. While all old writers remain stopped, set `SKL_DRAGON_MONGO_CUTOVER=1`, `SKL_DRAGON_MONGO_CUTOVER_RECEIPT` and destination environment for every backend instance, then launch the updated backend. Before scheduler admission, the runtime checks the private receipt, remote verified migration marker and collection UUIDs. Invalid configuration holds crawler sessions and commands; it never redirects writes to old collections. User/account lookups still use core DB. Verify application readiness, authorization, source consent, existing session readback, command/quota consistency, recovery and application routes. Do not disable the cutover switch after destination writes without performing a new reconciled migration—old data may be stale.

Only ordinary standalone/replica-set primary topology, simple string _id and B-tree indexes with the explicitly supported options are handled. TTL, custom collection options, sharded-cluster routing, views, unusual BSON IDs, unsupported index types require separate migration. This is not online/change-stream replication, full Mongo server relocation, live storage capacity proof, or migration of the whole app. Runtime verifies topology at startup; later replacement/credential changes require operator shutdown and requalification. Source collection metadata and raw BSON scan evidence are not signed attestation. Exact-head unit/real Mongo fixture results and production host execution are independent acceptance gates. The optional real-server integration suite requires SKL_DRAGON_RELOCATION_TEST_MONGO_URL pointing to a disposable Mongo server; fixtures generate unique test database names and remove only those names.
