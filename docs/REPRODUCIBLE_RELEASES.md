# Reproducible releases

Skeleton release packaging is treated as a verifiable build product rather than an opaque CI side effect.

## Reproducibility contract

The `Reproducible Release` workflow builds the same Git object twice from two clean checkouts in one pinned toolchain environment. Both builds use the commit timestamp as `SOURCE_DATE_EPOCH`, fixed locale/timezone/hash-seed settings, and exact Python/build/backend versions.

Setuptools source distributions are normalized after build by `scripts/normalize_sdist.py`. The normalizer uses only the Python standard library and rewrites tar/gzip timestamp and ownership metadata to deterministic values derived from `SOURCE_DATE_EPOCH` before provenance is emitted. This closes the backend-level sdist timestamp gap without weakening the byte-for-byte release requirement.

A release is considered reproducible only when the two independently generated artifact sets have identical names, sizes, and SHA-256 digests. The workflow compares both generated provenance documents and `SHA256SUMS` files and fails closed on any mismatch.

## Published evidence

A verified workflow run publishes one artifact bundle containing:

- the normalized Python source distribution and wheel;
- `release-sbom.cdx.json`, a deterministic CycloneDX declaration SBOM for the project and its declared runtime dependencies;
- `release-provenance.json`, which records the exact source Git object, source-date epoch, Python/build/setuptools/wheel versions, SHA-256 hashes for build/dependency inputs and the sdist normalizer, SBOM references, and every release artifact digest;
- `SHA256SUMS`, suitable for independent artifact verification and later signing/attestation workflows.

Release metadata is generated by `scripts/release_provenance.py`, which uses only the Python standard library. Metadata keys and input/artifact ordering are deterministic.

## Dependency and toolchain inputs

`requirements-build.txt` is the build-tool lock for release packaging. `pyproject.toml` pins the setuptools/wheel backend versions used by isolated builders as well. Provenance hashes those files, the runtime dependency declaration in `requirements.txt`, and `scripts/normalize_sdist.py`, making the complete deterministic packaging path attributable to a release.

Runtime dependency ranges remain application compatibility policy; they are not silently rewritten by the release job. If a full runtime lock is introduced later, add that lock file as another `--input` so its digest becomes part of the provenance contract.

## Local verification

From a clean checkout, install the pinned build tools, set the source epoch from Git, build, and normalize the sdist before recording provenance:

```bash
python -m pip install -r requirements-build.txt
export SOURCE_DATE_EPOCH="$(git show -s --format=%ct HEAD)"
python -m build --no-isolation --outdir dist
python scripts/normalize_sdist.py --source-date-epoch "$SOURCE_DATE_EPOCH" dist/*.tar.gz
python scripts/release_provenance.py sbom \
  --pyproject pyproject.toml \
  --output dist/release-sbom.cdx.json \
  --source-commit "$(git rev-parse HEAD)"
mkdir -p release-meta
python scripts/release_provenance.py emit \
  --artifacts-dir dist \
  --output release-meta/release-provenance.json \
  --checksums release-meta/SHA256SUMS \
  --source-commit "$(git rev-parse HEAD)" \
  --source-date-epoch "$SOURCE_DATE_EPOCH" \
  --input pyproject.toml \
  --input requirements-build.txt \
  --input requirements.txt \
  --input scripts/normalize_sdist.py \
  --sbom-ref dist/release-sbom.cdx.json
(cd dist && sha256sum -c ../release-meta/SHA256SUMS)
```

To compare two independent builds, run:

```bash
python scripts/release_provenance.py compare \
  build-a/release-provenance.json \
  build-b/release-provenance.json
```

## Release rule

Do not publish or sign a package if the clean rebuild comparison fails. A reproducibility mismatch is release-blocking evidence of uncontrolled build input, generated metadata, file ordering, timestamps, or toolchain drift and must be resolved rather than allowlisted.
